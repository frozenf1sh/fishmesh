# R6I-28/R6I-29：R6H 高负载长上下文双层滚动重启复验

## 结论先行

本轮针对旧 R6H 的 `TTFT P95 431.42 -> 100.32 ms` 结果，复用相同的 6 场景高负载矩阵，并对每个 arm
同时滚动重启 vLLM 与 Gateway，隔离 vLLM prefix cache、Gateway KV hash/index、subscriber 和 admission
runtime state。

有效数据共两组实验、四个 arm、`3136/3136` 请求成功：

| 实验 | admission | cache-salt | LB P95 | KV P95 | 变化 | Bootstrap 95% CI |
| --- | --- | --- | ---: | ---: | ---: | --- |
| R6I-28 | active，16/8/64 | steady-warm | 642.48 ms | 707.13 ms | +10.06% | [-1.29%, +21.32%] |
| R6I-29b | off，64/8/64 | 未启用 | 658.99 ms | 709.66 ms | +7.69% | [-0.82%, +16.61%] |

两组结果方向一致，说明 active admission 不是旧 R6H 收益消失的主要原因。当前实现即使在旧 R6H 的高负载
形态下，也没有复现 `-76.7%` 的 pooled P95 收益；但 R6I-29b 的 CI 跨 0，不能把 `+7.69%` 宣称为稳定
回归。

## 与旧 R6H 的差异

旧 R6H 的工作负载确实相同：`same/different/mixed × 4 KiB/12 KiB`，每个 run 392 请求，客户端并发
8/16，Gateway 64 in-flight、16 upstream connections，两个 mixed 场景各 100 请求且实际为 60% 热共享、
20% unique、20% 其他共享前缀。

但运行时仍有两个不能忽略的差异：

1. 旧 R6H 使用 `fishmesh-gateway:r6i1-load-gates-r1`，本轮使用当前
   `fishmesh-gateway:r6i24-admission-kv-bypass-r1`；这是服务镜像级差异，不能把结果归因到单个最近提交。
2. 旧 R6H 的四个 formal run 复用同一组 vLLM/Gateway 进程，属于 warm-cache A/B；本轮每个 arm 都重启两层
   cache state。R6I-29b 在 arm 内仍观察到 KV cached samples `784/784`，但没有继承前一个 arm 的缓存。

因此，本轮排除了“旧 arm 的残留缓存污染导致旧收益”的解释，但尚未单独拆出“旧 Gateway 镜像行为”与“跨 arm
warm-cache 条件”的贡献。

## R6I-29b 分场景结果

以下为两轮 run-level P50/P95 平均值；每个场景共 192 个请求。

| 场景 | LB P50/P95 ms | KV P50/P95 ms | P95 变化 | E2E P95 变化 |
| --- | ---: | ---: | ---: | ---: |
| same-4k | 56.05 / 143.66 | 67.72 / 118.98 | -17.18% | -7.95% |
| same-12k | 63.35 / 212.22 | 74.87 / 134.34 | -36.70% | -46.01% |
| different-4k | 180.14 / 229.18 | 190.22 / 256.75 | +12.03% | +19.51% |
| different-12k | 561.71 / 765.55 | 562.41 / 824.23 | +7.67% | +15.02% |
| mixed-4k | 122.83 / 334.31 | 126.92 / 365.29 | +9.27% | +43.07% |
| mixed-12k | 185.18 / 962.20 | 132.99 / 975.78 | +1.41% | +17.89% |

当前版本仍表现出明确的 locality 形态：same-prefix 的长上下文尾延迟改善，different-prefix 和 mixed
场景没有形成稳定的 pooled 尾延迟收益。旧 R6H 的 mixed-4k/mixed-12k 大幅收益没有在当前镜像、当前
cache 生命周期下重现。

R6I-29b pooled Gateway 窗口：

| 指标 | LB | KV-aware | 变化 |
| --- | ---: | ---: | ---: |
| 成功 | 784/784 | 784/784 | 0 |
| TTFT P50 | 130.69 ms | 119.34 ms | -8.68% |
| TTFT P95 | 658.99 ms | 709.66 ms | +7.69% |
| TTFT P99 | 979.53 ms | 1045.69 ms | +6.75% |
| accepted QPS | 18.160 | 18.359 | +1.10% |
| average in-flight | 9.116 | 9.289 | +1.90% |
| Little's Law W | 501.96 ms | 506.70 ms | +0.94% |
| rejection QPS | 0 | 0 | — |

KV `784/784` 请求为 `available` 并记录 cached-prefix sample；没有 KV degradation。两轮平均 Gateway
process window 的 RSS start/peak/end 为 LB `32.54/39.32/36.92 MiB`、KV `36.92/68.92/43.42 MiB`；Go
heap start/peak/end 为 LB `3.95/9.97/6.41 MiB`、KV `3.72/34.30/11.86 MiB`。KV 的 absolute peak
相对 LB 高约 `29.60 MiB RSS`、`24.32 MiB Go heap`，仍是 KV-aware 运行时近似上界，不是 hash-only exact
bytes。

## 有效性边界

- R6I-28、R6I-29b 均使用两个 seed、反向 arm 顺序、vLLM `maxSurge=0/maxUnavailable=1`，每个 arm 独立
  vLLM generation 和 Gateway runtime annotation。
- R6I-28 使用当前 active admission 和 steady-warm cache-salt；R6I-29b 关闭 admission 且不启用 cache-salt，
  更接近旧 R6H 运行口径。
- R6I-29 的第一次 off overlay 尝试因当前镜像要求 `admission initial target <= max in-flight` 而在正式请求
  前失败，随后改为有效的 `64/8/64` 配置并以新 rollout id 重跑；失败尝试不计入任何结果。
- 当前实验没有 vLLM Pod GPU utilization/runtime exporter，因此不把 GPU 饱和程度作为本轮已验证事实。
