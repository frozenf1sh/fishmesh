# R6I27 KV 状态一致性修补

日期：2026-08-16

## 背景

审计确认 vLLM 进程在同一 Pod UID/IP 内重启后，事件 sequence 会从 0 重新开始。原实现把所有
小于期望值的 sequence 都当作重复事件，因此旧 index 和旧 replay freshness 可能继续被使用。
同时，stored event 的已有 engine→request 映射没有一致性校验，查询侧也会在首个 block miss 后继续
计算整条 request hash 链。

## 实施

- sequence 发生“接近 0、明显小于旧 sequence”的回绕时，清理该 Pod 的 index，重置 sequence 建档，
  清空 replay freshness，并保持 `sequence-reset` 无效状态直到新的 replay END；新增 reset 计数指标。
- `applyStored` 在 Add 前校验已存在的 engine→request 映射；不一致返回
  `engine-request-key-mismatch`，由 lifecycle 清理 Pod index，并通过 `kv_event_errors_total` 计数。
  尚不存在的 engine key 允许作为新映射创建。
- 查询按 block 生成 canonical hash 并立即查 index，首个 miss 即停止后续 hash；完整请求 block 数仍
  用于区分真实零命中和不完整查询。

## 验证

- kvcache contract tests 覆盖 sequence 4→0、清理、freshness、replay 恢复和 reset observation。
- vLLM index tests 覆盖已有 engine/request mismatch 以及首个 query miss 后停止 hash。
- Gateway metrics tests 覆盖 sequence reset 和 key consistency error 指标。
- 已通过 `go test ./internal/serving/...` 与 `git diff --check`。

## 边界

本阶段没有增加“replay 长期零事件但 live 持续有 stored”启发式告警；该信号需要明确时间窗口和
低误报策略。sequence reset 清空旧 freshness 后，原 P1 场景不会继续显示 `Valid=true`。
