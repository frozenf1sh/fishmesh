# 04｜Pod→Node/GPU 身份映射与故障状态

## 目标

在把 GPU 信号纳入调度前，先证明每个动态 backend 对应哪个 Pod、哪个 Node，以及该 Pod
声明了多少 GPU 资源；同时让 EndpointSlice/API 暂时不可用时的风险可见，并在缓存过期后
停止接收新请求。

## 实现

- EndpointSlice 的 `targetRef` 保存在 backend metadata 中；
- 新增 Kubernetes identity provider，一次 list namespace-scoped Pods，批量映射：
  `backend ID → Pod → Node → declared GPU request`；
- `BackendObservation` 增加 identity/status/error 字段；
- Gateway `/metrics` 增加 Pod、Node、GPU request 和 discovery freshness/status；
- EndpointSlice resolver 记录最近成功时间、resourceVersion、错误和 Ready backend 数量；
- watch 之外增加 bounded periodic relist，避免无事件长连接阻塞权限/API 恢复；
- `/readyz` 规则：API 暂时断连但快照未过期时继续服务；超过 `FISHMESH_ENDPOINT_MAX_AGE`
  后返回 503；
- 实验 RBAC 仅新增 namespace-scoped Pod `get/list`，没有授予 Node、Secret 或写权限。

## 为什么暂时不读取 Node/GPU 实时利用率

Pod 的 `spec.nodeName` 和 GPU request 可以安全建立身份链路，但 DCGM/NVIDIA exporter 通常
提供节点级或设备级指标。没有 exporter 的 Pod/device label 映射前，把节点利用率复制到每个
backend 会造成错误调度证据。本阶段只建立身份，不把 GPU 利用率偷偷当成 Pod 指标。

## 验证计划

正常路径检查每个 backend 的 `pod_name`、`node_name` 和 `backend_gpu_requested`；故障路径
临时移除实验 RoleBinding，确认 discovery status 变为 degraded，缓存超过 30 秒后 `/readyz`
变为 503；恢复 RoleBinding 后 periodic relist 在约一个刷新周期内让状态和 readiness 恢复。

## P0 后的下一步修订

当前两个 Pod 使用同一张 time-sliced RTX 4060，DCGM device 指标不能可靠归因到单个 Pod。
因此不再把 GPU exporter 对齐作为下一步。身份链路保留用于故障解释；调度器下一步实现
eligibility filter、bounded affinity、queue/local-load spillover 和 Service fallback。
