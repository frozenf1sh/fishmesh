# 阶段 20：R6B-2 真实 KV 状态域

> 日期：2026-08-12
> 类型：Lite MVP 核心状态能力
> 状态：已完成
> 产品边界：交付 kvcache owner，暂不接 Gateway 和 routing

## 1. 本阶段真正交付什么

`internal/serving/kvcache` 只拥有一件事：**哪些完整 KV blocks 当前可靠地属于哪些 backend**。
它接收已经由 tokenization 生成的真实 Token IDs，返回逐 backend 的最长公共前缀；同时管理
vLLM Pod 实例、事件 sequence、replay heartbeat、freshness 和索引回收。

这个 domain 不读取 HTTP 请求体、不选择 backend、不实现 load-aware fallback，也不把 unknown/stale
伪装为零命中。requestpath 将在后续阶段根据 typed degradation 决定是否退回负载路由。

## 2. 固定契约与不变量

1. backend 稳定 ID 与 vLLM topic 中的 Pod identifier 分开保存，Pod UID 才是实例生命周期身份；
2. `Match.Valid=false` 与 `MatchedTokens=0` 语义不同；前者不能参与 exact routing；
3. sequence 只有在事件已经同步应用到 index 后才能提交，不能在 worker queue 入队时提前提交；
4. live gap 先失效，再从最后连续 sequence 的下一位 replay；buffer 无法覆盖时清空该 Pod 并保持
   invalid；
5. 空闲 vLLM 没有业务事件，freshness 只由成功收到 replay END 的主动心跳刷新；
6. Pod UID 改变或 backend 被移除时，先停止旧 subscriber，再按旧 Pod identifier 清理 index；
7. index key、每 key backend 数、实例数、单事件大小、单次 replay 数和 query token 数全部有上限；
8. cache salt 按 vLLM 语义只混入每个 prompt 的第一个完整 block；
9. 任何 decode、unsupported event 或 apply 失败都会清空该 Pod，避免部分状态产生错误 exact hit；
10. `Close` 取消并等待全部 goroutine，不留下 subscriber 或 ticker。

## 3. 为什么不直接使用上游 Event Pool

截至 2026-08-12，`llm-d-kv-cache` 最新发布仍为 `v0.9.0`；上游 main 的 `kvevents.Pool` 仍使用
没有容量配置的 workqueue，`AddTask` 也没有处理完成回执。R6A 探针在入队前推进 sequence，只适合
证明信号链路，不能直接成为生产可靠性实现：remove 事件尚未真正应用时，lookup 仍可能读取旧命中。

FishMesh 不 fork 或重写整套开源实现。本阶段继续复用上游：

- vLLM msgpack/parser 和通用 event 类型；
- canonical token block hash 与 cache-salt/extra-key 兼容格式；
- 有界 in-memory index；
- longest-prefix scorer。

FishMesh 只拥有缺失的 transport/lifecycle 语义：ZMQ 同步背压、apply 后提交 sequence、replay
heartbeat、gap 恢复和 Pod UID 清理。这个边界也是回答“为什么不用现成开源组件”的核心工程理由。

## 4. 当前文本 MVP 兼容边界

第一版只接受阶段 18 已真实验证的 vLLM 0.23 文本 GPU cache 事件：canonical block size 与 engine
block size一致，不支持 LoRA、HMA、多模态和 CPU offload。遇到这些事件时明确使该实例失效，而不
进行可能错误的近似解释。后续能力必须在真实兼容门禁通过后单独扩展。

## 5. 本阶段不做什么

- 不修改 Gateway、requestpath 或 routing；
- 不引入 Redis、Controller、CRD 或共享索引；
- 不复制 simulator KV event；
- 不重复 R6A 的 GPU 性能实验；
- 不升级无关的 llm-d Router 或其他技术栈。

## 6. 实际实现

### 6.1 稳定值对象和 owner

新增 `internal/serving/kvcache`，对外提供：

- `Instance`：backend ID、Pod UID、事件 Pod identifier、model 和实时/replay endpoint；
- `Query`：model、cache salt、独立 prompt token groups 和候选 backend；
- `Match/Snapshot`：逐 backend 的 Valid、typed reason、完整命中 blocks/tokens 和 freshness；
- `InstanceState/StateSnapshot`：已应用 sequence、replay 时间、event lag 和生命周期状态；
- `Index`：`Lookup/Reconcile/State/Close` 四个能力；
- `Config`：所有 index、event、replay、query 和 subscriber 上限。

返回的 match/state map 均为副本。routing 后续只能读取这些值对象，不能修改 index 或 subscriber。

### 6.2 同步事件提交

每个实例只创建两条可关闭 goroutine：一条 live subscriber，一条 replay heartbeat。live 和 replay
共用同一个同步处理锁，单条事件的流程固定为：

```text
校验 topic/大小/连续 sequence
  -> 上游 vLLM parser 解码
  -> 上游 canonical block hash
  -> 上游 bounded index Add/Evict/Clear
  -> 成功后提交 last_sequence
```

这保证 `last_sequence=N` 的含义是“N 已经可以被 Lookup 观察到”，而不是“N 只进入了一个未知长度
的异步队列”。live 事件处理速度不足时，ZMQ reader 的固定有界队列形成背压；FishMesh 没有增加
第二个无界 channel/workqueue。

### 6.3 replay 和 freshness

首次登记实例后立即从 sequence 0 replay。以后从最后连续 sequence 的下一位请求：

- 收到重复事件：忽略并计数；
- live 跳号：立即 `sequence-gap-awaiting-replay`，不推进 sequence；
- replay 能补齐到观察到的 gap：收到 END 后恢复 valid；
- replay 首条仍大于请求 sequence：清空该 Pod 并保持 `unrecoverable-sequence-gap`；
- replay 超过单次容量：清空并保持 `replay-capacity-exceeded`；
- replay 网络失败：不伪造心跳，超过 TTL 后快照自然变成 `replay-heartbeat-stale`。

### 6.4 Pod UID 生命周期

`Reconcile` 先校验实例数量和 backend/UID/topic 唯一性。Pod UID 或 endpoint 变化时：

1. 旧流立即 invalid；
2. cancel 并等待旧 live/replay goroutine；
3. 按旧 Pod identifier 清空全部 index entry；
4. 发布新实例，再从 sequence 0 开始 replay。

因此 Pod IP 即使被新实例复用，也不会继承旧 UID 的 locality。

### 6.5 cache salt 与事件兼容

查询侧把 cache salt 追加到每个 prompt 的首个完整 block extra-key。后续 block 通过 parent hash chain
自然隔离。该表示与上游事件 parser 对 vLLM `extra_keys` 的处理一致；不同 salt 的相同 tokens 不会
互相命中。

生产 adapter 遇到 LoRA、HMA、非 GPU tier 或不同 engine block size 时返回
`unsupported-event` 并清理该实例。这个选择比“尽量解析后继续路由”更安全，因为部分理解一个
cache event 会产生错误 exact hit。

## 7. 验证

13 个聚焦测试覆盖：

- Config、实例身份和 query 容量；
- unknown/stale 与 valid zero miss 的区别；
- apply 失败时 sequence 不推进且部分 index 被清理；
- live gap、完整 replay 恢复和无法覆盖的 replay gap；
- replay heartbeat freshness 和单次 replay 容量；
- cache salt 隔离、BlockRemoved 后前缀归零；
- 不支持的 engine 语义显式失效；
- Pod UID 替换先停止、再清理；
- lookup 与 lifecycle reconcile 并发；
- ZMQ live/replay frame 和 END sentinel；
- 原子 domain 只能依赖 `backend` 的架构门禁。

完成时执行完整仓库门禁：

```text
go test -race ./...
go vet ./...
go build ./...
make manifest
```

本阶段没有访问集群。阶段 18 已用同一固定版本 parser/hash/index 和真实 vLLM 事件验证 wire 数据；
本阶段新增的是生产背压、sequence commit 和生命周期语义，不重复没有新信息的 GPU smoke。

## 8. 尚未交付的产品行为

Gateway 还没有创建 `kvcache.Index`，tokenization 结果也没有进入 `Lookup`。当前部署仍然是 bounded
affinity，不能描述成 exact KV routing。本阶段同样没有创建 Kubernetes Pod watcher；后续
requestpath 组合会把 discovery/Pod UID 数据显式翻译成 `kvcache.Instance`。

## 9. 下一阶段

R6B-3 只修改纯 `routing` domain：

1. 增加 exact cache match、queue/running 和 hard overload 输入；
2. 先排除 ineligible/overload backend，再最小化 uncached tokens 和负载；
3. unknown/stale exact signal 不等于零命中，由后续 requestpath 决定整体降级；
4. session affinity 只在 exact 平局或降级时作为稳定提示；
5. 不接 HTTP、ZMQ、Kubernetes 或 Gateway。
