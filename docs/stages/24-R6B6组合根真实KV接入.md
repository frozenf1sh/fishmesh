# 阶段 24：R6B-6 组合根真实 KV 接入

> 日期：2026-08-12
> 类型：真实集群诊断与组合根交付
> 状态：已完成

## 1. 本阶段契约与不变量

1. 组合根是 Kubernetes EndpointSlice、Pod UID、ZMQ endpoint 与 `kvcache.Instance` 的唯一交汇处；routing 与 requestpath 不得认识 ZMQ 或 Kubernetes 细节；
2. 默认模式仍为 `session-key`；只有显式 `kv-aware` 才建立 KV subscriber，并且所有 unknown/stale 情形继续走既有 load-balanced 降级；
3. 文本 Qwen 的单一 full-attention KV group 可以归一化为当前无 group 的本地 index：仅当 `group_idx=0`、`kv_cache_spec_kind=full_attention` 且没有 sliding-window 元数据时成立；
4. LoRA、非零 group、非 full-attention group、sliding-window、非 GPU tier 或 engine block size 不一致仍必须使实例 `Valid=false` 并清理 index，绝不能产生近似 KV-aware hit；
5. sequence 仍只在事件同步写入 index 后推进；replay END 才刷新 freshness，不能为了兼容 group 而削弱该语义。

## 2. 先取证，再定位

当前 baseline Gateway 为 `session-key`，没有启用 kvcache，也没有对外的 kvcache 状态或指标端点。真实 EndpointSlice 已证明每个 Ready 地址都带完整 `targetRef.uid`，因此 UID → Instance 映射前提成立。

启用临时 KV-aware overlay 后，vLLM 0.23.0 实际启动参数、topic 和 endpoint 为：

```text
topic=kv@10.42.1.159:8000@qwen2.5-0.5b-instruct
events=tcp://10.42.1.159:5557
replay=tcp://10.42.1.159:5558
```

生产 subscriber 实际收到 replay 的 `sequence=0`；所以 topic 不匹配、ZMQ 不可达和 replay 请求/END 协议不是当前阻塞点。R6A 探针与生产实现都使用 `DEALER + 空 delimiter + 8-byte big-endian sequence`，并以 `MAX_UINT64` 为 END sentinel。

首个真实请求的头部仍为 `X-Fishmesh-KV-Status: match-unavailable` 与
`X-Fishmesh-Route-Reason: kv-aware-signal-unavailable`。新增仅诊断日志后，直接原因确定为：

```text
reason=unsupported-event
block_size=16 expected=16
lora_id_set=false lora_name_set=false
group_idx=0 kv_cache_spec_kind="full_attention" sliding_window=<nil>
```

原实现把任何非 nil `group_idx` 一概按 HMA 拒绝，导致 Apply 失败、sequence 不提交、replay 无法确认 freshness，最终 `Valid=false`。R6A 只验证 parser/上游异步 pool，因此未覆盖这一同步 index 兼容边界。

## 3. 下一步

同包 contract test 先失败后通过，实际实现只归一化 `group_idx=0/full_attention/no-window`：存储与移除
事件均可进入既有无 group 的本地 index；非零 group、sliding-window、LoRA、非 GPU tier 和 block size
不一致仍保持 `unsupported-event`。

## 4. 真实集群验收

临时 overlay 的 Gateway 使用 `kv-aware`；两个 Ready vLLM Pod 的 EndpointSlice UID → IP 映射均
完整。发送两个**不带 session key**的 SSE 请求，system prompt 完全相同、user message 分别为 `first` 和
`second`：

| 请求 | 关键响应头 | 结论 |
| --- | --- | --- |
| 首请求 | `X-FishMesh-KV-Status: match-unavailable`、`X-FishMesh-Policy: kv-aware-load-fallback-v1`、`X-FishMesh-Route-Reason: kv-aware-signal-unavailable`、`X-FishMesh-Cached-Prefix-Tokens: 0` | KV 信号尚未确认时，按既有 load-balanced 语义显式降级。 |
| 第二请求 | `X-FishMesh-KV-Status: available`、`X-FishMesh-Policy: kv-aware-v1`、`X-FishMesh-Route-Reason: kv-aware`、`X-FishMesh-Cached-Prefix-Tokens: 160`、`X-FishMesh-Upstream: 10.42.1.159:8000` | 在同一真实 vLLM Pod 命中 160 个缓存前缀 token。 |

vLLM 日志同时记录第二请求前的 prefix-cache hit rate 为 16.5%。这证明闭环为
`Render → EndpointSlice/Pod UID reconcile → ZMQ replay/live apply → Lookup → kv-aware → SSE`，而不是
session-key 提示。验收后恢复基础 `session-key` overlay；默认运行模式没有改变。
