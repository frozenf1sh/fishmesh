# 阶段 19：R6B-1 真实分词能力域

> 日期：2026-08-12
> 类型：Lite MVP 产品能力切片
> 状态：已完成
> 产品边界：只交付 tokenization domain，暂不接入 Gateway 和 KV index

## 1. 本阶段为什么先做它

FishMesh 要根据真实 KV cache 路由，首先必须知道“这个请求经过目标模型的 chat template 后，究竟
对应哪些 Token IDs”。客户端 session key、文本 hash 和估算 token 都不能替代这个事实。

本阶段把 R6A 中一次性探针调用 vLLM Render API 的逻辑，收敛为可被请求路径复用的生产能力。它
不是新实验，也不决定 backend；它只负责提供可靠、模型一致且资源有界的 prompt profile。

## 2. 固定契约

`internal/serving/tokenization` 必须满足以下边界：

1. 只支持明确声明的 OpenAI Chat Completions 和 Completions 路由；
2. 请求中的 model 必须与当前 renderer 配置一致，不能把一个模型的 Token IDs 用于另一个模型；
3. 保留请求中的 `cache_salt`，供下一阶段构造隔离后的 KV block key；
4. token 结果以只读值对象发布，调用方不能修改 domain 内部保存的 slice；
5. 请求体、响应体、总 token 数和单次调用时间都有硬上限；
6. client cancellation 和 deadline 必须继续通过 `errors.Is` 判断；
7. 非 2xx、响应过大、响应格式错误、模型不一致和不支持能力分别返回 typed error；
8. vLLM 返回多模态 features 时先明确返回 unsupported，避免只使用文本 Token IDs 产生错误的
   KV-aware 命中。

这个 domain 不读取 Kubernetes，不订阅 KVEvents，不选择 backend，不实现 fallback，也不处理
HTTP/SSE 客户端响应。

## 3. 实际交付

### 3.1 稳定能力契约

新增 `internal/serving/tokenization`，对外只暴露以下核心概念：

- `Input`：原始推理 route 和 JSON body；
- `Tokenizer`：一次 `Tokenize` 调用，不泄漏 vLLM 或 KV library 类型；
- `Result/Prompt`：model、cache salt 和一个或多个 token 序列；
- `Config/Dependencies`：模型、Render 地址、timeout、资源上限和注入的 HTTP client；
- `Error/ErrorCode`：请求错误、上游不可用、上游拒绝、响应错误和资源越界等稳定类别。

`Result` 内部持有 token slice，访问器返回副本。这样下一阶段即使并发查询 KV index，也不会因为
某个调用方误改 slice 而污染另一个评分过程。

### 3.2 vLLM Render adapter

adapter 根据原始 route 显式调用：

```text
/v1/chat/completions         -> /v1/chat/completions/render
/v1/completions              -> /v1/completions/render
```

实现不会重新定义 Chat message、tools 或 vLLM 扩展字段，而是保留原始 JSON 顶层字段，只校验并
固定 `model`，再读取 `cache_salt`。这避免 FishMesh 每次 vLLM 增加兼容字段时都维护另一套庞大
请求结构。

Chat 返回一个 prompt；Completions batch 可以返回多个 prompt。响应在发布前统一检查 model、
`token_ids`、多模态 features 和总 token 上限。

### 3.3 明确降级而非错误 KV-aware

当前 Lite MVP 只承诺文本请求。若 Render 返回多模态 hash/placeholder，adapter 返回
`unsupported_feature`。原因是 vLLM 的多模态 KV block key 不只依赖文本 Token IDs；忽略这些
输入会把实际不同的图片错误地判断为同一缓存前缀。

这不是永久删除多模态能力，而是把尚未完成的能力诚实地降级。以后可以在 tokenization 值对象和
上游 `llm-d-kv-cache` adapter 之间增加完整 extra features 映射，再单独解除限制。

## 4. 验证

12 个聚焦测试覆盖：

- Config、route 和 JSON 基本契约；
- 结果 slice 不可被调用方修改；
- Chat wire、Completions batch 和未知扩展字段透传；
- 请求/响应 model mismatch；
- `cache_salt` 类型和保留；
- 非 2xx、请求体上限、响应体上限和 token 总数上限；
- client cancellation、adapter deadline 和错误链；
- 多模态显式 unsupported；
- `tokenization` 不依赖其他 FishMesh internal package 的架构门禁。

完成时执行仓库要求的完整验证：

```text
go test -race ./...
go vet ./...
go build ./...
make manifest
```

本阶段没有访问集群。R6A 已经证明目标 vLLM 0.23.0 Render wire 可用；这里新增的是可复用产品
实现和本地协议边界，不重复进行没有新信息的 GPU smoke。

## 5. 尚未交付的产品行为

Gateway 仍未调用这个 domain，当前线上行为仍然是 session-key，不能描述为 KV-aware routing。
本阶段也没有创建 renderer Service；Lite 最终是复用每个 vLLM `serve` 的 Render API，还是配置一个
稳定的同模型 Render Service，将在 requestpath/deploy 接入时以最小运行拓扑决定。

## 6. 下一阶段

R6B-2 只建立 `internal/serving/kvcache` owner：

1. 先定义逐 backend `Match`、freshness、snapshot 和 typed degradation；
2. 用薄 adapter 复用 `llm-d-kv-cache` 的 vLLM 事件解析、block key 和 index；
3. 在 FishMesh lifecycle 层补齐 R6A 已确认的 sequence gap、replay heartbeat 和 Pod UID 清理；
4. 对 index key、每 key backend 数、subscriber 和 replay buffer 设置容量上限；
5. 不接 Gateway、不改 routing 公式、不再增加一次性探针。

完成 kvcache domain 并独立提交后，才进入 kv-aware 纯策略。
