# 07｜工程优先方向章程

## 背景

P0 修正了不成立的 GPU/eBPF/weighted-score 假设，但 README 和路线仍然以“研究何时 affinity
有效”为主语，并把完整实验系统排在标准集成之前。代码已经具备真实请求路径和 Kubernetes
生命周期能力，文档却容易让项目被理解为调度论文或 benchmark 平台。

## 本阶段决策

- 项目主语改为 Kubernetes-native LLM inference traffic scheduler；
- 工程完成标准改为可靠性、资源有界、标准集成、可操作性、自动 E2E 和可交付性；
- 实验只允许决定方案、验证验收或防止回归，不再形成独立产品路线；
- standalone Go Gateway 保留为开发、conformance 和演示载体；
- EPP/llm-d integration 从附加项提前到 request-path reliability 之后；
- `fishmesh-analyst` 冻结功能扩展，避免 scheduler、AIOps 和 Agent 多线发散；
- 原始 benchmark、日志和集群转储留在 Git 之外，仓库只保存可复现配置、代码和评审结论。

## 固化方式

新增 `docs/design/project-charter.md` 作为方向的最高优先级依据。任何新增常驻服务、数据库、
CRD/Controller、集群写权限，或把延期技术重新加入 MVP 的提案，都必须先更新章程并回答：

1. 解决哪个已复现的用户问题；
2. 改善哪项工程能力；
3. 为什么不能直接复用开源；
4. 新增什么状态、权限和故障模式；
5. 如何验收和回退。

## 下一阶段边界

只实施 request-path reliability：transport error circuit、endpoint state GC、admission 和
connection bounds、cancellation/retry boundary、per-field sample。完成 simulator fault E2E
后进行 EPP/llm-d integration spike。完整性能矩阵不阻塞这两个阶段。
