# 阶段 56：容量阶梯与拒绝证据

## 1. 目标

让 QPS/并发实验可以直接回答“Gateway 接受了多少、拒绝了多少、请求完成了多少、平均占用多少”，并提供一份
可替换运行元数据的 open-loop capacity ladder。

## 2. 实现

- Gateway metrics window 新增 `admission_rejections_total`，报告输出 rejection delta/rate；
- sampler 按正式 batch 分段，`batch_pause_ms`、scenario gap 和 warmup 都不计入 active elapsed；
- 多段聚合时 counter delta 求和，平均 in-flight 按 active duration 加权，accepted/completed/rejected rate
  使用同一 active window；
- 新增 [`configs/capacity-ladder.json`](../../configs/capacity-ladder.json)，覆盖 1/2/4/8/16/32 offered QPS，
  使用 2048 prompt-token、256 output-token、concurrency 16 和两批次；
- capacity ladder 只是一份运行模板，必须替换 run nonce、vLLM generation，并通过
  `--metrics-endpoint <Gateway /metrics>` 采集 Gateway 事实；
- rejection/counter reset/缺失指标仍只让 metrics report invalid，不改变请求路径。

## 3. 采集命令

```bash
fishmesh-client bench \
  --plan configs/capacity-ladder.json \
  --metrics-endpoint http://<gateway>/metrics \
  --metrics-interval 250ms \
  --run-nonce <unique-run> \
  --cache-generation <vllm-generation>
```

正式结论必须保留 plan、requests JSONL、report JSON/Markdown、Gateway metrics window 和失败分类；不能只
报告平均 TTFT 或 offered QPS。GPU/容器负载仍是独立观测证据，不进入本阶段路由评分。

## 4. 验证

- Prometheus parser 覆盖 completed status 求和与 admission rejection counter；
- 分段窗口覆盖 batch pause 排除、加权 in-flight 和 rejection rate；
- 本地完整 Go、manifest 和 diff 门禁；
- 本阶段没有执行真实 GPU 压测，因此不声称容量拐点或生产 QPS。
