# 阶段 61：运行时负载硬安全门接入路由

## 1. 交付

- requestpath 将已归属、仍 fresh 的 runtime sample 翻译为可选 hard safety gate。
- 支持 CPU cores、memory bytes、GPU utilization percent、GPU memory bytes 和 GPU temperature 的独立阈值。
- 任一配置阈值被超过时，backend 标记为 `RuntimeHardOverload`；load-balanced/KV-aware 都在存在替代项时先排除它。
- 所有阈值默认是 0（关闭）；runtime sample 缺失、过期、NaN/Inf 或没有 Pod 归属时不触发硬门。

## 2. 为什么先做硬门而不是加权 score

CPU、显存、GPU utilization 和温度不是同一量纲，且 GPU exporter 的 Pod 归属在 time-slicing 环境可能不成立。当前实现只把明确超过阈值的 fresh sample 当作安全信号，不把多个不可靠数值拼成伪精确的综合分数。所有候选都过载时仍保持 availability-first，沿用现有最小压力选择。

## 3. 配置

```text
FISHMESH_RUNTIME_CPU_HARD_LIMIT_CORES=0
FISHMESH_RUNTIME_MEMORY_HARD_LIMIT_BYTES=0
FISHMESH_RUNTIME_GPU_UTILIZATION_HARD_LIMIT_PERCENT=0
FISHMESH_RUNTIME_GPU_MEMORY_HARD_LIMIT_BYTES=0
FISHMESH_RUNTIME_GPU_TEMPERATURE_HARD_LIMIT_CELSIUS=0
```

这些阈值只有在第 58 阶段 runtime Prometheus collector 配置并通过真实 freshness/identity 验收后才应启用。

## 4. 验证

- 单测覆盖 fresh mapped runtime over-limit、healthy sample、invalid/unmapped sample 和普通路由排除。
- 本阶段未启用默认部署阈值，未把 runtime signal 用作 weighted score，也未在共享 time-sliced GPU 上宣称独立利用率收益。
