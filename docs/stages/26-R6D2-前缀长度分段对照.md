# 阶段 26：R6D2 前缀长度分段对照

> 日期：2026-08-12
> 类型：有限真实集群 profile 尝试
> 状态：已完成（受控 512/2048 两档；后续长度不扩展）

## 1. 固定方案与已完成取证

尝试复用既有双 vLLM 副本、direct K8s Service、`exact-cache-load` 和默认 loadgen。每个长度
`512 / 1024 / 2048 / 3072` 使用八个均匀 prefix group；每个 group 起初定向预热到一个 Pod：512、
2048 到 `10.42.1.171`，1024、3072 到 `10.42.1.173`。预热不改 loadgen 的默认 200 requests、并发
4、max tokens 32、keep-alive false 或热度分布。

现有 R6A probe 对真实 endpoint 每长度测量 20 次 Render + lookup：

| prefix bytes | Render P50/P95 ms | lookup P50/P95 ms |
| ---: | ---: | ---: |
| 512 | 4.715 / 5.394 | 0.117 / 0.173 |
| 1024 | 5.114 / 5.674 | 0.166 / 0.238 |
| 2048 | 5.550 / 6.229 | 0.210 / 0.272 |
| 3072 | 5.957 / 6.911 | 0.316 / 0.383 |

这只是已存在 probe 在同一 vLLM/上游 index 上的实际计时；不是 Gateway 新指标，也不能被称为
per-event KVEvents latency。

共产生 26 个 200-request HTTP/SSE attempt，原始 JSONL 保留在实验机和本地 `/tmp/r6d2-*.jsonl`，
不进入 Git。原计划的 24 个 length×treatment×3 attempt 都 200/200 成功；剩余列表错误重复了
`exact-512-r1` 与 `service-2048-r1` 两个成功 attempt，重复原始文件另存为 `.duplicate.jsonl`，不纳入
三轮汇总，不能静默覆盖。

## 2. 为什么不能发布收益/拐点表

该尝试**没有满足 c=1 固定场景**。虽然每个 group 最初只预热到一个 Pod，但随机交叉中的 direct
Service attempt 会经 ClusterIP 把同一 prompt 写入另一 Pod；后续 exact records 因而出现预热目标以外
backend 的 `exact-cache-load-v1` 选择。例如原应预热到 `endpoint-3f413dc4f08a` 的 512-byte groups，
400 个 exact-policy requests 中有 173 个选择 `endpoint-e41578831fdf`。这使 cached-token share 与
hit/miss TTFT 不再能归因到单副本（c=1）缓存，不能用它推导 prefix-length benefit 或“超过约 10 ms
路由开销的拐点”。

direct vLLM Service 也不返回 backend 或 cached-prefix response header；现有 loadgen 因而只能记录
Service 总体 TTFT 与两个 Pod 的累计 `prompt_tokens_cached_total` delta，不能对每条 Service request
可靠分列 hit/miss。不能用累计 counter 或 TTFT 阈值事后猜测分类。

## 3. 真实正确性降级证据

在 exact 第三轮期间，Gateway logs 记录两个 backend 的 live KV event apply failure：

```text
backend=endpoint-e41578831fdf sequence=5382 reason=event-apply-failed
error="resolve parent block: engine key not found: 10910333396747814245"
backend=endpoint-3f413dc4f08a sequence=7216 reason=event-apply-failed
error="resolve parent block: engine key not found: 6811078848178777324"
```

Gateway metrics 随后显示两个 instances `Valid=0`、reason=`event-apply-failed`；每个长度第三个
exact attempt 的 200 个请求全部正确写为 `exact-load-fallback-v1` / `exact-signal-unavailable`，没有
错误 exact cache 声明。这证明降级语义保持正确，但这些 800 个成功 HTTP/SSE 请求不是可用于 exact-hit
性能样本的资料。

## 4. `engine key not found` 诊断（2026-08-12 暂停）

### 4.1 已查证的协议与索引语义

vLLM 0.23 的 `BlockStored` wire event 依次携带 `block_hashes`、`parent_block_hash`、
`token_ids` 与 `block_size`；这里的 hash 是 engine 分配的 64 位 block hash，而不是 FishMesh
计算的 token hash 或物理 block id。`llm-d-kv-cache` v0.9.0 先将每个 engine hash 映射到由
token/model/parent 计算的 canonical request key；带非零 `parent_block_hash` 的后续 stored event
必须先以该 engine hash 查询 parent request key，再生成子 request key。

本次错误恰好发生在这一步：`GetRequestKey(parentEngineKey)` 找不到映射。上游对普通
`BlockRemoved` 的未知 engine hash 是明确 no-op（其回归测试也覆盖此情况），因此**不能**把本次
parent resolution failure 归类为“清缓存/eviction 后的预期边界”。现有证据只支持“subscriber/index
缺少该父块的 stored mapping”，可能来自 replay 窗口、事件丢失/重排、索引清理与 live event 的组合；
还没有原始 wire batch，不能在这些可能性间猜测。

### 4.2 最小复现受外部节点状态阻塞

按本阶段要求准备执行单副本、一个简单请求流的最小复现之前，`fishmesh-gpu` 从控制面视角变为
`NotReady`：Lease 最后续约为 `2026-08-12T14:00:22Z`，Node condition 为
`NodeStatusUnknown/Kubelet stopped posting node status`，并有 `node.kubernetes.io/unreachable`
`NoSchedule`/`NoExecute` taint。两个原 vLLM Pod 已进入 Terminating，替代 Pod 因 GPU 节点不可
调度而 Pending；直接 SSH 到 `100.98.49.106:22` 亦在 8 秒超时。

因此既没有一个可用 vLLM Pod，也无法从节点取得 vLLM publisher/replay 原始 batch；继续 rollout 或
用旧日志推断都会混入节点断联/Pod 终止。按“先取证、后定位”与 ZMQ/sequence 不猜测约束，本阶段在
此暂停。现有 Gateway 的 `event-apply-failed → Valid=false → exact-load-fallback-v1` 降级保持不变，
没有为实验改动任何产品逻辑。

节点恢复后，最小复现的首要取证项是保存同一 backend 的 replay 和 live 原始 batch（sequence、
`parent_block_hash`、`block_hashes`），并在每次 `Clear`/rollout 前后核对 parent mapping 是否仍存在；
只有证明 parent event 已被消费却映射被错误移除，才讨论最小修复。否则将其作为 replay/订阅边界记录。

### 4.3 节点恢复后的单副本最小复现

节点恢复后先确认 `bounded-affinity`、Gateway 1/1 与 vLLM 2/2 Ready，再短暂切至既有 exact
overlay 并把 vLLM 缩为一个副本。该副本的最小两请求流没有复现 failure：首请求发生在 replay
确认前，正确得到 `match-unavailable` / `exact-load-fallback-v1`；随后 index 为 `Valid=true`，sequence
从 1 推进到 2，第二个相同 system prefix 请求得到 `available` / `exact-cache-load-v1` 与 16 个
cached prefix tokens。期间 applied batches 从 2 到 3，没有 Gateway `event-apply-failed` 日志。

这只证明普通、连续的 parent→child stored 流能被当前 adapter/index 正确处理，不能把此前双副本、
高事件量下的缺失 parent mapping 解释为 eviction 边界，也不足以定位一个可修最小点。时间盒内没有
进一步 wire-level 证据，故保持原有 invalid 降级、不开猜测性修复；获批的性能对照可继续，但任一
新的 `event-apply-failed` 都会保留 attempt 并立即停止该批实验。

### 4.4 受控对照的首个失败 attempt

按批准协议短暂恢复双副本后，执行一次 vLLM controlled rollout 清除两个 cache，再把 512-byte、
8 个均匀 group 的 200 个默认 loadgen 请求**定向**预热到新 Pod `10.42.1.187`；预热为
200/200 成功，原始 JSONL 保存在实验机 `/tmp/r6d2-l512-exact-prewarm.jsonl`，不进入 Git。

但是该 rollout 之后，EndpointSlice 已正确列出两个新 Ready Pod（`10.42.1.187` 与
`10.42.1.188`），Gateway KV metrics 却持续只有已删除的旧 backend
`endpoint-4e3c2accb8b2`，其状态为 `replay-heartbeat-stale` / `Valid=false`；等待一个完整
discovery/replay 周期也没有建立新实例或推进新 sequence。故该 attempt 的实际 c 无法验证，更不
满足 exact signal available，**没有发送 200-request exact treatment**，不能用 fallback 代替。

这揭示了受控 cache-clear rollout 必经的 EndpointSlice → instance/subscriber lifecycle 缺陷；它也可能
解释此前双副本压力下的事件状态异常，但尚没有 subscriber 建立/退出与原始 ZMQ batch 的对应证据，
不得猜测修复。按本次时间盒和“无日志证据变化即暂停”规则，分段对照在第一项停止。

### 4.5 修复契约与不变量

定位到的最小缺口是 requestpath 的后台 membership reconcile 只更新 strategy、circuit 与本地
in-flight state；`KVReconcile` 只在某个 exact HTTP request 的 `buildExactInput` 内调用。因此 vLLM
rollout 后，即使 EndpointSlice 已变为新 Pod，Gateway 在第一条业务请求前仍持有旧 subscriber，
无法满足“等待 replay valid 后再发 treatment”的实验契约。

修复只改变 requestpath 的后台编排：每次成功取得 discovery snapshot 时，exact 模式也必须将同一份
backend membership 交给 `KVReconcile`；该后台失败只保持 exact unknown/降级，绝不阻断 discovery、
circuit 或普通请求路径。前台 `buildExactInput` 仍保留 reconcile，保证关闭后台周期或刚发生 membership
变化时的第一条 exact 请求也不会使用过期 instance。回归测试将锁定：无业务请求的周期 reconcile 会调用
KV reconcile 并携带新 backend；其错误不影响其它 membership 维护。

## 5. 负载纪律、恢复状态与继续条件

本轮单副本最小复现、vLLM rollout 与一次 200-request 预热始终保持 loadgen 默认并发 4，未并行运行
GPU load。`nvidia-smi dmon -s pucv -d 10` 从双副本恢复前启动并在实验收尾时停止；记录到温度峰值
62°C（短时 100% SM、67 W），没有持续超过 80°C，也没有 `gpu-watchdog` WARN/CRITICAL。结束时 GPU
已回落为 46°C、0% 利用率、约 5 W。

实验后已声明式应用 `deploy/experiments/r6d-bounded-affinity`，确认
`FISHMESH_ROUTING_MODE=bounded-affinity`，Gateway 1/1、vLLM 2/2 Ready。

R6A 临时 probe 已停止。若人工决定继续，应先针对 vLLM rollout 后 EndpointSlice instance reconciliation
取证：记录 discovery snapshot、新/旧 Pod UID、subscriber start/stop、replay request/END 与每个
backend 的 metrics；仅当新 backend 实例可用且 c=1 已由 lookup/header 验证后，才重启对应单一
treatment。这个组件根 lifecycle 行为属于真正不确定的架构/行为问题，在定位前不重跑、不调参、
不提交“收益拐点”结论。

若 lifecycle 问题修通，正确的实验协议仍须在**每一个 treatment attempt 前**清空两个 vLLM KV caches、
仅向一个确定 Pod 预热八个 groups、等待 Gateway replay valid 后立刻运行单个 treatment；Service 和
exact 不可在同一缓存世代随机交叉。

### 5.1 修复后的受控两档对照

实际修复是让 requestpath 的成功 discovery reconcile 同步调用 `KVReconcile`，而不再只在第一条
exact HTTP request 中创建/替换 subscriber。KV reconcile 失败不会撤销 discovery membership；它只令
exact 信号维持 unknown，从而继续选择 `exact-load-fallback-v1`。同包 race contract test 锁定“无业务
请求的后台周期也传递新 membership”与“replay 错误不破坏普通 membership”。真实 vLLM rollout 后，
零业务请求条件下 Gateway 已自动淘汰旧实例并建立两个新 backend，二者均为 `Valid=true/ready`。

受时间与温度纪律限制，采用任务允许的两档优先方案：512 与 2048 bytes；每个 treatment 前均受控
rollout 清空两个 vLLM cache，只向一个新 Pod 定向预热八个均匀 group 的默认 200 requests，再以 R6A
probe 验证 c=1，最后执行该 treatment 的一轮 200 requests、并发 4、max tokens 32、keep-alive false。
Service 与 exact 不在同一 cache generation 交叉。所有八份 prewarm/treatment JSONL 保留在实验机
`/tmp/r6d2-*-fixed*.jsonl`，未进入 Git；四个 treatment 都 200/200 成功。

| prefix bytes | treatment | TTFT P50 / P95 ms | prewarm 后 sampled cached-token share | c 验证（目标 Pod / 另一 Pod） | Render + lookup P50 ms |
| ---: | --- | ---: | ---: | --- | ---: |
| 512 | direct Service | 31.274 / 35.442 | 112 / 138 = 81.16% | 112 / 0 tokens | 6.015 + 0.129 |
| 512 | FishMesh exact | 24.429 / 24.936 | 128 / 142 = 90.14% | 128 / 0 tokens | 5.935 + 0.123 |
| 2048 | direct Service | 31.859 / 37.059 | 448 / 472 = 94.92% | 448 / 0 tokens | 6.206 + 0.608 |
| 2048 | FishMesh exact | 25.279 / 26.680 | 480 / 493 = 97.36% | 480 / 0 tokens | 6.671 + 0.289 |

这里的 cached-token share 是每组预热后的真实 Render+KV lookup 样本（而不是无逐请求标签的累计
vLLM counter）；它用于验证 c=1 与 shared prefix 可见性，不能扩展为 200 条请求的逐条 hit rate。exact
响应在这两个有效 attempt 中均保持 `available/exact-cache-load-v1`，没有出现
`event-apply-failed` 或错误 exact 声明。

| prefix bytes | exact 相对 Service P50 | exact 相对 Service P95 | P50 绝对收益 | 相比约 10 ms routing overhead 的结论 |
| ---: | ---: | ---: | ---: | --- |
| 512 | -21.89% | -29.98% | 6.845 ms | 小于 Render+lookup 约 6.06 ms 后仍不足 10 ms |
| 2048 | -20.65% | -28.01% | 6.580 ms | 小于 Render+lookup 约 6.96 ms 后仍不足 10 ms |

因此，在已测两档中 exact 相对 Service 有稳定 TTFT 改善，但**不存在“收益超过约 10 ms routing overhead”
的最小前缀长度**；不能从 512/2048 插值声称 1024/3072 的拐点。没有调高 max tokens、降低并发或重排
workload 来放大差异。

环境边界保持不变：单 RTX 4060 time-slicing、Qwen2.5-0.5B、两个共享 vLLM 副本、loadgen 同 GPU
node；即使后续控制修复，结果也只可作为 correctness/profile evidence，不能声称生产性能。
