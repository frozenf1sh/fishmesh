# 阶段 21：R6B-3 缓存/负载联合纯路由

> 日期：2026-08-12
> 类型：Lite MVP 纯策略切片
> 状态：已完成
> 产品边界：交付 routing contract、kv-aware 策略和 requestpath 降级语义；不接 Gateway、Render 或 KVEvents lifecycle

## 1. 本阶段真正交付什么

`internal/serving/routing` 新增纯 `kv-aware` 策略。它只解释调用方发布的稳定值对象：prompt token 总数、逐 backend KV-aware prefix match、queue/running/local in-flight 与 hard overload；不读取 HTTP、Kubernetes、ZMQ、时间或第三方 cache/token 类型。

`requestpath` 同时明确 KV-aware 信号不可用时的语义：任一 eligible backend 的 match unknown/stale 时，绝不伪装成零命中，而是使用 load-balanced，返回 `kv-aware-signal-unavailable` 和 `kv-aware-load-fallback-v1`。本阶段只定义和测试该边界，不创建 tokenizer、index 或 Gateway 依赖。

## 2. 固定契约与不变量

1. routing 只拥有 `KVAwareInput`、`KVMatch`、`Load`；`kvcache.Match`、`tokenization.Prompt/TokenIDs` 与第三方类型不得进入 routing contract；
2. requestpath 边界负责将只读 TokenIDs 的 token count 和 kvcache 的 `Match.Valid/MatchedTokens` 投影为 routing 值对象；
3. `KVMatch.Valid=false` 是 unknown/stale；只有 `Valid=true, MatchedTokens=0` 才是可用于 KV-aware 的真实 zero miss；
4. KV-aware 仅在每个 eligible backend 都有有效、范围正确的 match 时运行；否则 requestpath 显式降级到 load-balanced；
5. 策略先排除 ineligible、再排除 hard overload，随后最小化 uncached tokens；只在 KV-aware 平局时比较已知 queue、running 和 local in-flight，session key 仅作最终平局提示；
6. 缺失 load sample 不伪装成零负载；它排在同一 KV-aware locality 的已知 load 之后；
7. 所有 eligible backend 都 hard overload 时，cache locality 被否决，以既有 load-balanced 顺序保留可用性并返回 `hard-overload-fallback`；
8. 不修改 Gateway、KV subscriber、Pod lifecycle、body replay 或 llm-d adapter。

## 3. 实际实现

`Snapshot` 增加 `KVAware` 和 `Loads`；`KVAwareInput.UsableFor` 集中校验 prompt token、候选覆盖、`Valid` 与 match 范围。注释固定后续转换所有权：requestpath 使用 tokenization 的只读 TokenIDs 计算 `PromptTokens`，逐字段投影 kvcache `Match`，routing 不反向依赖两个叶子 domain。

新增无状态 `NewKVAware`。比较为可解释的词典顺序：

```text
eligible -> non-hard-overload -> minimum uncached tokens
         -> known queue -> known running -> local in-flight -> session tie-break
```

`requestpath.Request` 接收转换后的 `routing.KVAwareInput`。配置 KV-aware 策略时，requestpath 在调用策略前检查所有 eligible candidates；输入不完整时调用 load-balanced 并重标记 typed reason/policy，避免以后 Render 失败或 KV replay stale 时误称 KV-aware routing。

## 4. 验证

同包 contract tests 覆盖：

- valid zero match 与 unknown match 的不同语义；
- 最少 uncached tokens，及 queue/running/local in-flight 的 KV-aware 平局顺序；
- hard overload 否决更高 cache locality；
- requestpath 在 unknown KV-aware signal 下显式降级到 load-balanced；
- routing 仍只依赖 backend/observation，requestpath 未引入 HTTP、ZMQ 或第三方类型。
